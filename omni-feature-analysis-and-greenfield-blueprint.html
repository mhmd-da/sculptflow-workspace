Bottom line

Omni’s product surface is broad and valuable — WhatsApp-first omnichannel messaging, campaigns, an agent inbox with bots, and a real commercial layer — but most of its cost comes from enterprise machinery that the Omni product alone does not need: ~40 services, a ~450-topic broker, trigger-driven cache replication, ~2,000 stored procedures, an own SMPP gateway, two inbox products and multi-product identity and billing. Two developers should rebuild the capabilities, not the architecture: a modular monolith on PostgreSQL with one message model, one ledger and one job mechanism, keeping the proven ideas (reserve → settle, SKIP LOCKED claiming, rank-based statuses, idempotent claims) and fixing the recurring failure modes (ack-before-work, in-memory state, silent retries, unverified webhooks). MVP ≈ 6–7 months; conversational product ≈ 2–3 months after.

01Current Omni at a glance

Omni (Monty Mobile “Single Interface”) is a multi-tenant omnichannel communications platform (CPaaS + customer-engagement suite). Businesses use it to send and receive messages on many channels, run marketing broadcasts, serve customers in a shared agent inbox, automate conversations with bots, and pay for all of it through wallets, rate cards and packages. It is sold directly and through resellers and white-label operators.

Business purpose

  • Transactional messaging API (OTP, notifications) — pay per message.
  • Marketing broadcasts on SMS, WhatsApp, Viber, RCS, Email, Push, voice.
  • Conversational support: agent inbox, bots, AI knowledge-base assistants, web chat.
  • Commercial layer: prepaid/postpaid wallets, rate plans, packages with quotas, payments, reseller margins.

Actors

  • Client admin (business) — campaigns, templates, contacts, channels, billing, reports, APIs, webhooks.
  • Agent / supervisor — inbox, assignment, transfers, notes, analytics.
  • Reseller — clients, packages, classes, rates/costs, sender management, accounting.
  • Platform admin / support — providers, routes, approvals; a separate support portal over prod data.
  • Customer systems (API keys, webhooks) and AI agents (MCP tools).

Channels

  • WhatsApp Cloud API (direct Meta Graph) — the 2026 focus.
  • SMS one-way and two-way — own SMPP gateway + ~23 HTTP vendor adapters.
  • Viber (via an aggregator), RCS (Google RBM), Facebook Messenger, Instagram.
  • Email (tenant SMTP / Office 365), mobile push (FCM), web live-chat widget.
  • Voice/SIP OTP (proof of concept), HLR/MNP number lookup (sold as a product).

Architecture, data, infrastructure in one paragraph each

General architecture

About 40 .NET 8 microservices (38 registered in the QA service registry), each a layered API or worker, communicating over Apache Pulsar (~450 topics) and sharing one PostgreSQL database in which most business logic lives as ~2,000 stored functions. An Ocelot gateway fronts the APIs. The same images are deployed many times: per channel, per priority, per product and per white-label customer.

Databases & state

PostgreSQL (AWS RDS in prod) with ~31 schemas in the Omni DB (~840 tables in QA, 86 GB) — CDRs, logs and derived summaries dominate volume. MongoDB holds bot vectors and history, MinIO holds media and exports, Redis holds inbox caches, access-control verdicts and MCP sessions, Keycloak holds identities. Most services also keep large in-process caches kept in sync by a trigger-driven replication system (UpdateTracker).

Infrastructure & deployment

GitLab CI per repo (~37 pipelines with SAST, Sonar, container and DAST scans) builds images with Kaniko and writes kustomize overlays to a GitOps repo for Kubernetes. Config is injected as whole appsettings files from CI variables; 20+ private NuGet packages carry the shared framework. Logging goes to Elasticsearch/Seq (Serilog) and files/Postgres (log4net); OpenTelemetry exists only in the newest services.

Important cross-service flows

  • Broadcast: portal → notification-service (validate, price, reserve money, enqueue) → queue-handler claims → outgoing handler / SMS router & gateway → provider → callbacks → CDR writer → Omni Core jobs settle money, update counters and summaries.
  • Transactional API: customer → gateway → notification-service → same path, on priority/OTP lanes.
  • Inbound conversation: Meta webhook → webhook-service → inbox-service (or Chatwoot) → bot-middleware/bot-service or dispatcher → agent via SignalR → reply → notification-service → outgoing handler.
  • Money: reserve (DB procedure at enqueue) → settle per message (Omni Core billing jobs + credit log) → wallet/quota confirm or release; subscriptions renew/expire daily.
  • Config propagation: DB triggers → UpdateTracker dispatcher → per-entity Pulsar topics → every pod patches its cache.

Channels, Senders & Onboarding 11 features · 2 major

How clients connect the identities they send from: WhatsApp numbers, SMS sender IDs, pages, agents and apps.

WhatsApp Business onboarding (Embedded Signup)BUILD MVP AConnect a client’s WhatsApp Business Account and phone numbers through Meta’s Embedded Signup, then register and subscribe them.
What it does

Lets a client connect their own WhatsApp Business Account (WABA) and phone numbers to Omni without manual Meta console work: code exchange for a token, long-lived token, token debug, phone registration, app webhook subscription, and business profile lookup.

Why it exists

WhatsApp is the channel that carries most of Omni’s 2026 product work (campaigns, inbox, bots). Self-serve onboarding removes a support-heavy manual step and is how every serious WhatsApp BSP works.

Services involved
notificationhandler, notification-service, omni-mm-react-gui
How current Omni handles it

The portal runs Meta’s Embedded Signup; the outgoing handler performs the Graph API calls synchronously (code → token → long-lived token → debug → register number → subscribe app). notification-service stores the resulting sender (phone-number id, WABA id) and app records and, depending on the reseller, auto-creates an inbox. Tokens are stored per reseller in client configuration and are copied onto every queued message row.

Important flow

Client clicks “Connect WhatsApp” → Meta popup → auth code returned to portal → backend exchanges code for token, fetches WABA and numbers → number registered and app subscribed to webhooks → sender + app rows created → inbox provisioned → templates synced.

Dependencies

Meta app (one per environment), webhook ingress, sender model, template sync, secret storage for tokens.

Benefits

Self-serve activation; fewer support tickets; unlocks templates, campaigns and inbox for the number immediately.

Drawbacks

Keep — BUILD · phase 1
Recommended new approach

Implement in the Channels module: an onboarding endpoint that completes the Embedded Signup exchange, stores the WABA/phone numbers as channel accounts, stores the system-user token in the secret store (encrypted column or vault), subscribes the app, and triggers an initial template sync job. Credentials are looked up by channel account at dispatch time, never copied into messages.

Messaging Core & Send API 10 features · 2 major

Accepting, validating and pricing every outbound message, whatever its source (API, campaign, agent, bot).

Transactional send API (single, bulk, OTP)BUILD MVP APublic API for clients to send single, bulk and OTP messages on SMS, WhatsApp, Email, Push and voice.
What it does

API-key authenticated endpoints to send single messages, bulk lists (limit ~1000) and OTPs per channel, plus “agent” variants used by the portal composer. Validates, prices, reserves money, and returns a message id per recipient.

Why it exists

The API is how most CPaaS revenue arrives (OTPs, notifications from customer systems).

Services involved
notification-service, Omni.APIGateway, notificationhandler, routing-service, smsgateway-mt
How current Omni handles it

Each channel has its own API service. Requests pass the gateway, a per-deployment channel kill switch, an IP whitelist, API resolution (client, sender, service, subscription), per-destination validation and pricing, then a DB procedure that locks wallet/quota and inserts queue rows; WhatsApp session messages and some channels publish straight to Pulsar “single/OTP” topics. There are two SMS code paths (a legacy GET path with per-sender traffic limits and a newer POST path).

Important flow

Client → gateway (API key) → validate & price → reserve money → message persisted/queued → dispatcher → provider → status callbacks → client webhook.

Dependencies

API keys, channel accounts, pricing & wallet, dispatch, status tracking, webhooks.

Dispatch & Provider Integrations 7 features · 2 major

Getting accepted messages to providers: queue claiming, provider adapters, throughput and retries.

Outbound dispatch pipeline (queue claim → provider call)BUILD SIMPLIFIED MVP AClaims due messages from DB queues, builds provider payloads and calls the provider for every channel.
What it does

Campaign rows are claimed from per-channel DB queues with a single-statement FOR UPDATE SKIP LOCKED claim, turned into channel payloads and published to per-channel send topics; the outgoing handler consumes those topics, calls the provider (Meta Graph, Google RBM, FCM, SMTP/O365, Viber aggregator, voice dialer) and publishes a “sent” result event.

Why it exists

Separates accepting a message from delivering it, so scheduling, pause, priority and provider slowness do not block the API.

Services involved
notification-queue-handler, notificationhandler, notification-service
How current Omni handles it

Quartz jobs whose cron and batch size are read from a DB table claim rows and mark them consumed before publishing. ~25 queue-handler deployments (channel × priority × product) and one outgoing-handler deployment per channel and product. Most provider calls are started without being awaited, so the broker message is acknowledged before the send completes. No retry, no rate limiting, binary sent/failed status.

Important flow

09Production lessons

Reusable engineering lessons extracted from code comments, fix commits, docs, the earlier AI investigations and the database. Each is phrased as the rule the new system should follow.

Duplicates & idempotency

  • Providers resend callbacks and the bus redelivers: duplicate WhatsApp sent rows and callbacks double-billed, closed invoice headers early and needed a 282-line remediation script.
  • Dedup must be a DB constraint on the business key (provider event id; message + status), not per-pod memory or Redis alone.
  • Clients retry too: without an Idempotency-Key on send, a retry duplicates the message and the money hold.

Retries & poison messages

  • A retry counter incremented inside a rolled-back block never moved — the same poison batch was re-claimed forever until Omni Core 2.5.7.
  • After the fix, retries exhausted silently: 36k push CDRs never billed and 102k never summarised in prod.
  • Webhook retries without an enforced policy reached 330 attempts over ~22 h; deleting retry rows before joining lost 1,031 retries.
  • Retry policy lives in one place, with max attempts, TTL, backoff, a parked state and an alert.

Ordering & races

  • Shared subscriptions with concurrent batches give no ordering: bot multi-part replies arrived out of order; status transitions arrive late or early.
  • Fold statuses with a monotonic rank; serialise per conversation for chat; never rely on arrival order.
  • Assignment had races (reopened-while-assigned, team changes on resolved conversations) — keep transitions in one place with tests.

Provider behaviour & outages

  • There is no provider failover: a failed SMS stays failed; the “re-route” publish is commented out.
  • Provider quirks: DLR ids in hex/decimal/zero-padded forms, receipts without text, time zones, operator encodings, Instagram vs Messenger profile fields (error #100).
  • Meta throughput limits (429) are not handled; reasoning LLMs can burn the whole budget and return empty content.
  • Linux TCP connects could hang — hard timeouts on every outbound call.

Delayed callbacks & money

  • WhatsApp reservations can stay locked up to 31 days before an expiry release — expiry is part of the money model.
  • A reservation must carry its own identity: every quota leak came from settling against a recomputed bucket (stale cycle key at launch; lock and release keyed differently; renew cancelling without quota release; paused-queue cleanup releasing twice).
  • Every cancel path calls one “void reservation” routine.

Broker, Redis & DB failures

  • A June 2026 consumer-hang incident drove a rewrite of the Pulsar handlers (async, semaphores, ack timeouts) — reliability was added reactively.
  • Infinite send timeout + block-if-full makes publishers hang while the broker is down.
  • Entitlement checks fail open when Redis/DB fails, with a 15 s negative TTL — the right trade-off for paid customers.
  • Wallet contention at 300–500 TPS on one account drove a 1 s lock timeout and a Redis POC — reserve per batch instead.

Worker restarts & stuck work

  • Messages claimed then not published stay “consumed” forever with money locked; the SMS gateway loses in-memory queues; bot flow position and large-campaign batch files vanish on restart.
  • Conversations stuck in the assignment queue needed event-driven retries and expiry.
  • Every claim needs a lease and a reaper; every long process needs a durable checkpoint.

Billing & quota consistency

  • Ledger rows once had no business reference (“OTHER, no reference”) — write entries with their reference in the same transaction.
  • Package edits vs live subscribers need revisions, “price changes next cycle” and customer notice.
  • Threshold alerts must be edge-triggered (once per crossing / recharge).

Caching & configuration

  • Cache invalidation is the most frequent bug class in routing; SMTP caching shipped without invalidation and caused a “null smtp config” hotfix.
  • A cache helper passed seconds where minutes were expected and used add-not-overwrite: “1 hour” meant “never expires”.
  • GUIDs differ per environment; per-tenant field-casing differences broke one environment at a time.

Scaling bottlenecks

  • Hot pickers over boolean flags on ever-growing tables took 74–95 s on 11M rows when a partial index didn’t match the predicate text exactly; ~420 MB of prod indexes never scanned.
  • Nothing is partitioned and archiving never ran — table growth is the main performance risk.
  • Per-pod SignalR registries and caches broke with more than one replica; the cross-pod router is a stub.

Deployments & migrations

  • Schema must deploy before writers whose COPY maps reference new columns.
  • Re-running an older routine file silently replaced a newer procedure on QA (Billing 2.0.44).
  • The migration pipeline recorded only 12 runs in QA — changes reached databases by other routes.

Security

  • Provider webhooks are accepted unsigned; OTP bypass lists leaked into prod once; profile updates could change roles; a merchant key was logged on every checkout until Aug 2026.
  • Check 2FA before creating the IdP session; never ship test backdoors in config.

10Recommended new architecture

Question: if two experienced developers built Omni today, keeping what the enterprise system learned but none of its baggage, how should it be designed? Answer: a modular monolith in .NET on PostgreSQL, deployed as one container image running in two roles (Api and Worker), with a React SPA. The database is the system of record and the work queue. No broker, no gateway, no Redis and no Kubernetes-specific machinery until measured need justifies them.

The shape

  • One repository, one solution, one image. Modules are folders/projects with enforced boundaries, not services.
  • Omni.Api: portal and public REST API, provider webhook endpoints, SignalR hub, auth.
  • Omni.Worker: every background loop — dispatch, scheduler, inbound processing, settlement, webhook deliveries, imports, AI ingestion.
  • PostgreSQL: module schemas, transactional outbox, job tables with leases, partitioned message events, pgvector.
  • Object storage (S3-compatible) for media, imports and exports.
  • React SPA: client portal, agent inbox and platform admin in one app with role-based areas.

Why this and not microservices

  • Two developers cannot operate ~40 services, a broker and 37 pipelines; the evidence shows even a large team struggled (drift, silent loss, stale caches).
  • Most current cross-service coupling is already through one database — a monolith makes that coupling explicit and transactional.
  • Transactions replace sagas: accept + price + hold + persist + outbox is one commit.
  • Debugging is one process, one log stream, one trace.
  • Volumes (single-digit millions of messages per month) are far below what one Postgres and a few workers handle.

Why two roles, not one process

  • Isolation: a campaign expansion or AI ingestion spike cannot slow the API or webhook acknowledgements.
  • Scaling: workers scale by replica count safely because every loop claims work with SKIP LOCKED leases.
  • It costs almost nothing: same code, a role switch in configuration. In development both roles can run in one process.

16Implementation guidance for selected features

Concise implementation guidance for the features the new Omni should build. It is written to be handed to Claude inside the new repository as design context: behaviour, placement, state, reliability and edge cases — no code.

Tenancy, identity & API keysPhase 0Features: Tenant → reseller → client hierarchy & white-label, Authentication (portal login, tokens, 2FA), Authorization (roles, scopes, menus), API keys & IP allow-lists
Desired behaviour

Client (workspace) is the tenant root. Users belong to one or more clients with a role. Portal uses cookie or JWT sessions with TOTP 2FA; integrations use API keys with scopes. Every request resolves a client context from the credential, never from a header.

Architectural placement

Identity + Accounts modules; authorization policies in the Api host; client_id filter applied by EF for all tenant-owned entities.

Main dependencies

Platform kernel (audit, settings), email sending for verification/reset.

Important state / flow

User: invited → active → disabled. API key: active → revoked/expired (prefix shown, secret hashed, shown once, last_used_at).

Reliability concerns

Rate limit per API key and per client (ASP.NET Core rate limiter); lockout after failed logins; audit every security event.

Important edge cases

User in several clients (switch workspace); key rotation with overlap; background jobs must carry client_id explicitly; platform admins crossing tenants must be audited.

Lessons from current Omni

Check 2FA before issuing a session; no test backdoors; profile updates must not change roles; permissions defined in code, not seeded per environment.

What is simpler

No realm per tenant, no auto-generated endpoint scopes, no eight API areas; a fixed role set with named permissions.

Outbox, job runner & schedulerPhase 0Features: Event bus (Apache Pulsar) with DB-driven topology, Scheduled jobs driven by DB rows, Retries, dead letters & poison handling, Multi-instance job coordination
Desired behaviour

Any module can enqueue work in the same transaction as its data. Worker loops claim jobs of a kind with FOR UPDATE SKIP LOCKED and a lease, run them, then mark done/failed with next_attempt_at. After max attempts a job is parked and an alert fires.

Architectural placement

Platform kernel; handlers registered per job kind by each module; scheduler (cron in code) enqueues timed jobs, guarded so only one instance enqueues each tick.

Main dependencies

PostgreSQL only.

Important state / flow

Job: queued → running (lease_until) → done | retry_scheduled | parked. Reaper returns expired leases to queued.

Reliability concerns

Handlers must be idempotent (keyed by business id); per-kind concurrency limits; backoff with jitter; poison isolation per item, not per batch.

Important edge cases

Long jobs extend their lease; clock skew (use DB time); deploys mid-job (lease expiry recovers); fairness across clients (ORDER BY priority, created_at with per-client caps).

Lessons from current Omni

Retry counters that don’t persist on rollback loop forever; silent exhaustion hides revenue loss; claim-before-publish without a lease loses work.

What is simpler

Replaces Pulsar, UpdateTracker dispatch, the request table, DB-configured Quartz and modulus sharding.

Send pipeline (accept → validate → price → hold → persist)Phase 1Features: Transactional send API (single, bulk, OTP), Destination validation & pricing pipeline, Priority lanes (OTP / transactional vs bulk), SMS encoding & segment counting
Desired behaviour

POST /messages accepts one message or a batch with channel, channel account, recipients, content or template + variables, client reference, priority and Idempotency-Key; returns 202 with message ids and per-recipient rejections.

Architectural placement

Messaging module in Api; pricing via Billing contract; suppression via Contacts contract.

Main dependencies

Channels (account, template), Contacts (suppression), Billing (price + hold), Platform (outbox).

Important state / flow

Message: accepted → queued → sending → sent → delivered/read (or failed/rejected/expired); every change appends a message_event.

Reliability concerns

What justifies each addition

Redis

A second Api instance (SignalR backplane) or rate limits that must be shared across workers. Not for general caching — in-process caches with TTL are enough.

More workers

Queue lag p95 above target (e.g. OTP > 5 s, bulk > campaign SLA) while the DB has headroom. Workers are stateless; add replicas, then split lanes into separate deployments.

Separate services

Independent scaling that replicas cannot give, a separate team owning a module, a different release cadence, or isolation required by contract. Extract along module seams — the contracts already exist.

Partitioning workloads

Message/event tables beyond ~50–100M rows or vacuum/index maintenance pain → monthly partitions (designed in from day one, so this is configuration). Claim contention → shard by channel-account hash.

A broker

Sustained >1–2k jobs/s on Postgres queues, the need to buffer inbound webhook storms independently of the DB, or external systems consuming event streams. Keep the outbox; the broker only changes transport.

Advanced infrastructure

Columnar analytics (ClickHouse/Timescale) when rollups and exports compete with OLTP; multi-region when contracts require it; SMPP when aggregator margins justify direct operator links.

21Open questions and uncertainties

Things that could not be determined confidently from code, docs or the DEV/QA databases. None of them blocks the recommendation; several change the order of the roadmap.

Product scope

  • Which channels carry real production traffic? Evidence suggests WhatsApp dominates Omni prod (SMS reporting tables in prod are near-empty) — confirm before choosing the Phase 1 channel.
  • Is the reseller tier (classes, packages on behalf, allocation, branches) used by paying tenants? It is the largest complexity driver in commercial code.
  • Are quota-based packages (free marketing messages, seats, bot tokens) used by real customers, or is wallet-only billing enough initially?
  • Which clients still use Chatwoot, and do they need migration into the native inbox?
  • Are payment links, failover, MCP tools, appointments and the form builder committed customer asks or speculative?

Volumes & SLOs

  • Actual production volumes per channel and peak TPS (only QA was surveyed; QA volumes were used as a proxy).
  • Required OTP latency and campaign throughput targets — these size worker lanes and rate limits.
  • How many concurrent agents and inboxes must the first inbox release support?

Operations

  • Which platform will host the new Omni (existing Kubernetes, ECS, App Service)? Who operates Postgres, secrets and monitoring?
  • How many replicas do inbox-service, bot-service and smsgateway-mt run in prod today (several have single-instance assumptions)?
  • Is the Pulsar broker backlog monitored, and does any consumer use Key_Shared ordering?

Technical

22Final summary

Recommended new Omni architecture

A modular monolith in .NET 10 with twelve enforced modules, shipped as one image in two roles (Api, Worker), on one PostgreSQL that is both system of record and work queue (outbox + leased jobs + partitioned message events + pgvector), S3-compatible storage and one React SPA. No broker, gateway, Redis or Keycloak until measured need.

MVP feature list

WhatsApp onboarding & templates; one send API (idempotent, priority lanes) for WhatsApp, SMS via aggregator and email; dispatcher with retries and rate limits; signed webhook ingestion and an out-of-order-safe status model; wallet with holds, price books and settlement; campaigns with contacts, imports, scheduling and opt-out; client webhooks; message logs, timeline and dashboards; sign-up, top-up, admin console.

Top features to reuse

  • Reserve → settle charging per message
  • SKIP LOCKED claiming (with leases)
  • Rank-based status folding
  • OTP lane separate from bulk
  • Idempotent claim ledgers & unique business keys
  • Price snapshot; block unpriced traffic
  • Bot-while-Pending + handover with context
  • Webhook delivery model

Top features to simplify

  • Campaigns → one entity, async expansion
  • Messages/CDRs → one table + events
  • Billing → one ledger with holds
  • SMS → aggregators + weighted route table
  • Inbox assignment → least-loaded + pull
  • RBAC → fixed roles, named permissions
  • Tenancy → client from token
  • Bots → webhook bot + deterministic flows

Features to build later

  • Campaign & provider failover (design now)
  • AI knowledge-base bot and flow builder
  • Plans, allowances & entitlements
  • Web chat widget; Messenger/IG, Viber, RCS
  • Short links & click tracking; two-way SMS
  • Reseller model, invoices, payment links, MCP tools, Verify API

Features to avoid initially

  • Own SMPP gateway, HLR/MNP, DLT
  • Pulsar and UpdateTracker
  • Chatwoot bridge
  • MCP agents, voice/vision AI, semantic cache
  • Shifts, event policies, capacity counters
  • Per-tenant deployments, FX, fees/taxes engine, appointments, form builder

Biggest lessons from existing Omni

  • Persist first, then acknowledge — never keep critical state only in memory.
  • Dedupe with database constraints on business keys.
  • A reservation needs an identity; settle against it exactly once.
  • Bounded retries must park and alert, not go silent.
  • Verify every inbound webhook; secrets never travel in messages or logs.
  • Plan table growth (partitions) and business-time semantics up front.
  • One implementation per capability; delete predecessors.

Recommended first development steps

  1. Confirm scope decisions in the open questions (Phase-1 channel, resellers, quotas, hosting).
  2. Create the repo skeleton: Api/Worker hosts, module projects, architecture tests, CI with migrations.
  3. Build the platform kernel: outbox, leased job runner, scheduler, audit, OpenTelemetry.
  4. Identity & accounts: login, 2FA, roles, API keys, client context from the token.
  5. Model messages, message events (partitioned) and the ledger with holds — then the WhatsApp adapter, signed webhook ingress and a provider simulator.
  6. Ship an internal alpha: send a template via API, see its timeline and the captured charge.
