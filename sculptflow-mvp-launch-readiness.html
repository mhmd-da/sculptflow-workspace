Is SculptFlow ready to launch as an MVP?

Read-only review of the main branch (HEAD 548a3de) plus the local tree, 30 Sep 2026. Covers the .NET backend, the Razor Pages frontend, the n8n integration points and the Supabase Postgres schema. No code was changed.

Verdict: launch a small pilot after a short must-fix list. Not ready for open signup yet.

The product itself is in good shape: the committed code builds cleanly (0 errors, 0 warnings), tenant isolation is enforced server-side, and the core loop (WhatsApp/Telegram in, AI reply, staff takeover, booking) is complete. What stands between it and real clinics is mostly security hardening and operational setup, not missing features. About half the must-fix items are a few lines each. With them done, a pilot with 1 to 3 hand-picked clinics is reasonable.

The time-handling rework (UTC in the DB, clinic/my-time switch) is still in progress and uncommitted locally (17 files). I treated it as in-flight work, not a finding. It just needs to be finished and pushed before launch.

Must fix before any real clinic uses it

Security1. Verify Meta's webhook signature

POST /api/integrations/whatsapp/webhook accepts any body from anyone (Controllers/WhatsAppWebhookController.cs:84, and the class comment says so). Someone who knows or guesses a clinic's phone_number_id can forge "customer" messages. That creates fake leads, opens the 24-hour window, and makes the AI send real WhatsApp messages from the clinic's number to any phone number they choose. Fix: read the raw body and check X-Hub-Signature-256 (HMAC-SHA256 with Meta:AppSecret) before processing. Roughly 20 lines.

Security2. Rotate the leaked secrets

N8n:IngestApiKey and Meta:WebhookVerifyToken are in git history (commit 2aec468), and the handoff notes that the Supabase DB password was shown in chat. The ingest key matters most. It is a master key: every /api/ai/* endpoint trusts whatever clinicId the caller passes, so holding the key gives read and write access to every clinic's leads, bookings and conversations. Rotate all three and update Render, n8n and Meta.

Database3. Give production its own database

Local development, live feature testing (test clinics registered and deleted with scratch tools) and the Render app all use the same Supabase database. Before real patient data goes in, create a separate production project, apply Database/schema.sql to it, point Render at it, and keep the current one for dev. Also confirm the Supabase plan includes daily backups, and ideally point-in-time recovery for medical-adjacent data.

Database4. Lock down Supabase's public Data API

schema.sql creates 35 tables in public and has no enable row level security statements at all. On Supabase, the auto-generated REST API exposes public tables to the anon key, which is designed to be non-secret. SculptFlow doesn't use that API, so the simplest fix is to turn the Data API off in the Supabase project settings. The other option is to enable RLS with no policies on every table. Before choosing that, confirm the app's connection role bypasses RLS (the postgres role does).

Security5. Close the open doors: signup, lead intake, test endpoints

  • Registration is open to anyone, with no email verification, CAPTCHA or rate limit. For a pilot, switch it off in Production and create the pilot clinics yourself.
  • POST /api/leads is [AllowAnonymous] with no ingest key and takes ClinicId from the body (Controllers/LeadsController.cs:30). Anyone can insert leads into any clinic. Nothing inbound uses it any more, so add [RequireIngestKey] or remove it.
  • /api/ai/test/* (AiTestController) is live in Production. It's inert, but it's easy to gate on IsDevelopment().

Hosting6. Behave correctly behind Render's proxy

There is no UseForwardedHeaders and no persisted DataProtection key store (Program.cs). Behind Render's TLS proxy the app thinks every request is plain HTTP. As a result, the login cookie isn't marked Secure, HSTS is never sent, and the app logs "Failed to determine the https port". Because the keys live inside the container, every deploy signs every user out and invalidates any calendar OAuth consent in progress. Fix: add ForwardedHeaders (proto and for) before the other middleware, and persist the keys to the database (PersistKeysToDbContext). About 10 lines.

Campaigns7. Campaigns need opt-out, and "Schedule" doesn't work

  • Nobody can opt out. Every lead created from an inbound WhatsApp or Telegram message defaults to MarketingOptIn = true (Services/LeadService.cs:260, 293). Nothing in the codebase ever sets OptedOutAt. There is no "STOP" handling and no staff control for it. So a reactivation campaign reaches everyone who ever messaged the clinic, with no way out. That breaks WhatsApp Business policy and can get the clinic's number quality-rated down or restricted. Minimum fix: honour "STOP" and unsubscribe replies, and give staff an opt-out toggle on the lead page.
  • Scheduled campaigns never send. The Create page offers "Schedule" (Pages/Campaigns/Create.cshtml:286), which sets the status to Scheduled. But no background worker picks those campaigns up, so they wait forever. Either add a small hosted service or hide the option for launch.

If campaigns aren't part of the pilot, hiding the Campaigns menu is an acceptable alternative to fixing both of these now.

n8n8. Finish and verify the patient-AI workflow end to end

The app side of the new booking tools is done (schedule_consultation, cancel_consultation, get_my_appointments, get_available_slots with leadId). According to the handoff, the n8n workflow still hasn't been moved over to them. The workflows aren't in the repo, so I couldn't review them directly. Before launch, move the workflow to the new tools, then run a full scripted conversation on a test number: ask a question, book, reschedule, cancel, hand off to staff, and get a 409 after takeover. Also turn on Header Auth for the trigger webhook. It currently needs Authentication = None, so the URL is the only thing stopping anyone from triggering AI turns. The app would need to send that header in AiTriggerNotifier.

Meta9. Confirm the Meta app can onboard other businesses

I can't check this from code. For clinics to connect their own numbers through Embedded Signup, the Meta app has to be Live, business-verified, and have advanced access to whatsapp_business_management and whatsapp_business_messaging (Tech Provider). It also needs a privacy policy URL and a data-deletion URL. The app has neither page today.

Should fix soon (pilot can start without them)

SecurityEncrypt stored tokens

WhatsApp access tokens, Telegram bot tokens and Google/Outlook refresh tokens are stored in plain text (channel_integrations.access_token, calendar_integrations.refresh_token). Once DataProtection keys are persisted (item 6), wrap these columns with a protector.

SecurityTighten the ingest-key trust model

Compare the key in constant time (RequireIngestKeyAttribute.cs and ConversationsController.SendMessage both use !=). Longer term, derive clinicId from the conversation instead of trusting the query parameter.

AccountsPassword reset and staff invites

There's no "forgot password" page and no email sender, and lockout is on (lockoutOnFailure: true). Staff can't be invited, so each clinic has exactly one login. That's workable in a pilot, where you can reset passwords by hand and clinics share a login, but it's the first thing real clinics will ask for.

OpsMonitoring, health check and hosting plan

There's no health endpoint, error tracking or uptime alert. n8n failures are logged and swallowed, so a broken AI flow goes unnoticed until a clinic complains. Add MapHealthChecks, an uptime ping and an error tracker. Also make sure the Render plan doesn't sleep when idle, because Meta webhooks and the scrape and benchmark workers need the app awake.

BackendDon't wait on n8n inside Meta's webhook

AiTriggerNotifier runs inline in the webhook request with the default 100-second HttpClient timeout. If n8n is slow, Meta times out and retries. Ingestion is idempotent, so retries are safe, but set a short timeout (5s) or hand the trigger to a background queue.

ProductHide or finish half-built surfaces

  • The Calendar Integrations page connects accounts, but appointment sync does nothing until the n8n sync workflow is built and N8n__CalendarSyncWebhookUrl is set. Label it "coming soon" or hide it.
  • "Generate Test Cases" in the Benchmark stays disabled until its n8n workflow exists. That's fine as an internal tool, but consider hiding it from clinics.
  • The manual WhatsApp connection form doesn't register the phone number.
  • Remove the deprecated /api/ai/appointments/book|reschedule once n8n has moved to the new tools.
  • A campaign send flips the conversation to human mode, so the AI stops answering people who reply to a reactivation campaign. Decide whether that's intended.

QualityTests and CI

There's no test project, and .github/workflows is empty. Every feature was verified by hand against the shared database. Two cheap wins: a build-on-push workflow, and a handful of integration tests for tenant isolation and the AI booking codes.

Repo hygieneKeep local keys out of commits

Properties/launchSettings.json is tracked in git and currently modified locally with real keys. The committed copy is clean. Move those values to user-secrets, or mark the file git update-index --skip-worktree, so a routine git add -A can't leak them. Also export the n8n workflows into the repo so they're versioned and reviewable.

CompliancePatient data basics

Plastic-surgery conversations are health data. Before going beyond a pilot you'll need a privacy policy, terms, a data processing agreement with clinics, a retention and deletion path for a patient's data, and a clear note that AI replies go through OpenAI (embeddings) and whichever LLM n8n uses.

What's already solid

  • The committed code builds cleanly: 0 errors, 0 warnings, from a fresh export of HEAD.
  • Tenant isolation: dashboard pages and APIs resolve the clinic from the logged-in user, never from the browser. The SignalR hub groups are resolved server-side.
  • The website crawler has a real SSRF guard: it validates connect-time IPs, re-checks every redirect hop, and doesn't use a proxy.
  • The frontend escapes server data before inserting HTML (escapeHtml in Inbox, textContent in the calendar and benchmark).
  • Telegram webhooks check a per-connection secret in constant time. Calendar OAuth uses a signed, time-limited, clinic-bound state.
  • Message ingestion is idempotent, the 24-hour WhatsApp window is enforced server-side, and the AI send re-checks the mode before sending.
  • Schema: all timestamps are timestamptz, there are 98 indexes covering the clinic-scoped queries, and closed sets have CHECK constraints.
