01Executive summary

Keep the application. Stabilize the messaging and tenant boundaries. Ship a clinic-focused omnichannel MVP. The repository is an implemented vertical product, not an empty MVC starter. Its useful assets are the WhatsApp/Telegram inbox, leads, appointments, templates, campaigns, and knowledge retrieval.

The best next investment is dependable execution of the flows already present. Keep .NET 10, ASP.NET Core Razor Pages and controllers, Identity, EF Core, PostgreSQL/pgvector, SignalR and the existing UI. Introduce durable acceptance, a small database-backed job mechanism, verified webhook ingress, safe status transitions and tenant-consistent relationships. Keep one deployable application initially; a separate worker is a later operational choice, not a prerequisite for architecture quality.

Scope assumption: first customers are clinics using the current product, with WhatsApp primary and Telegram secondary; a small shared team uses one connected account per channel per clinic. Retain clinic workflows as the differentiator. If the commercial objective is instead a general CPaaS, resolve that before Phase 3; do not prematurely remove working clinic features.

Immediate orderConcrete outcome
1. Close trust and data-integrity gapsVerify Meta POST signatures; bind machine credentials to clinic/permissions; reject cross-clinic lead/appointment references; make all booking entry points use the same guards.
2. Establish repeatable changes and failure testsBaseline the existing SQL schema, introduce ordered migrations, pin dependencies, and test the current boundary failures against disposable PostgreSQL.
3. Make one message durable end to endAccept once, commit a pending message and job, dispatch safely, persist every attempt/outcome, retain early callbacks, and expose uncertain results.
4. Apply that core to existing featuresMove staff/AI/template/campaign sends through it; deliver AI and calendar triggers durably; keep the current inbox and booking UX.
5. Release a bounded pilot, then MVPProve tenant isolation, restart recovery and provider failure behavior before enabling unattended marketing or expanding channels.

02New Omni today

It contains one .NET 10 web project, 190 C# source files, 31 Razor page/view files and 11 application JavaScript files (excluding generated output and bundled libraries). The UI is primarily Razor Pages, with JSON API controllers and a SignalR hub; “MVC solution” is a useful shorthand, but there is no separate SPA or API deployment.

Findings that should change the first sprint

FindingEvidence and precise limitImpact / action
F1 · Unverified WhatsApp POSTThe direct controller parses JSON and dispatches without checking the raw-body HMAC. The GET verify-token handshake exists. Evidence E3Subscription verification is not per-delivery authentication. Validate before deserialization and before any side effect.
F2 · Cross-clinic relationship creationConversation creation accepts a lead ID without checking clinic ownership. Appointment CreateCore checks procedure ownership but does not reject a foreign lead. Procedure-booking creation checks the procedure but not lead/appointment ownership. Foreign keys use object IDs without clinic equality. Evidence E5, E7, E10Static evidence supports invalid tenant relationships and possible navigation-based disclosure or mutation if a foreign ID is supplied. Exact exploit response not runtime-tested. Reject each mismatch and audit existing rows before tightening constraints.
F3 · Sends before persistenceStaff, AI and template paths call their provider before adding/saving the message. Evidence E2A crash, timeout or failed save creates ambiguous delivery. A database transaction cannot make a remote send atomic; retain intent and attempt identity, and never promise exactly-once remote delivery.
F4 · Status loss and regressionStatus handler returns not-found for unknown provider IDs; outer webhook acknowledges. Known messages and campaign recipients overwrite status directly. Evidence E2, E3Callbacks racing the send response disappear; delivered after read regresses. Persist raw events, correlate later, and use explicit transition rules.
F5 · Campaign concurrency and consentQueued recipients are selected without a lease; schedule has no runner; cancellation changes rows a concurrent batch may already hold; consent evaluated at creation only. Evidence E4Concurrent requests can duplicate sends and late opt-outs may still receive marketing. Dispatch-time validation and atomic claims precede unattended launch.
F6 · Window and AI gapsInbound window is set from processing time, even though provider timestamp is stored on the message. One AI trigger is selected for a multi-event Meta payload; notifier swallows failure; fresh AI mode check is not an atomic send gate. Evidence E2, E3, E5Delayed events may extend the window incorrectly, multiple inbound turns may not trigger, and takeover races remain. Use trusted event time, one durable turn per event and a serialized ownership decision.
F7 · Two booking pathsGuarded AI booking/reschedule acquires a clinic advisory lock and checks availability. Dashboard appointment POST uses CreateAsync directly. Evidence E7The existing good lock does not protect every writer. Preserve the guarded implementation and route all booking commands through it; explicit privileged overrides must still validate tenant and audit intent.
F8 · Single-process recovery assumptionsCrawl/benchmark recovery marks all running work interrupted at startup and requeues pending rows. Evidence E9A second host could mark another host’s live run failed or process it twice. Recovery is useful but not distributed coordination.
F9 · Reporting and ownership side effectsCampaign reply stats compare the earliest inbound in the whole conversation with send time; a separate RepliedAt field is also written. All template sends, including campaigns, force human mode. Evidence E2, E4Reply counts can miss genuine later replies; marketing can unexpectedly disable AI. Choose one attribution rule and distinguish proactive campaign sending from deliberate staff takeover.
F10 · Browser security and observabilityRazor Pages have framework antiforgery behavior; controller mutation paths do not show an explicit equivalent. Raw provider errors are included in some responses; tokens are plain integration fields. Evidence E1, E2, E6Treat controller CSRF protection as a gap, not proof that every JSON endpoint is exploitable. Add explicit validation, separate service authentication, and protect/redact credentials.

09What to keep, improve and postpone

What is good — keep

  • One deployable and one authoritative relational database.
  • Pages and API reuse the same services without HTTP calls to themselves.
  • Server-derived clinic membership and SignalR group checks.
  • Shared message/conversation model and two real channel adapters.
  • Transactional clinic registration; guarded appointment booking with clinic-level locking.
  • Provider identifiers and several useful unique indexes already exist.
  • pgvector retrieval and the crawler’s SSRF/size/robots protections.
  • Native inbox and useful clinic workflows; these are assets, not future greenfield tasks.

Clinic is the tenant root. Identity users link through clinic membership. Leads link to procedure interest, conversations, messages, appointments and procedure bookings. Messages carry channel, direction, origin, sender type, provider ID and optional campaign/template links. Campaigns have recipient snapshots; channel connections hold identifiers and tokens; templates/health events belong to a connection/clinic.
